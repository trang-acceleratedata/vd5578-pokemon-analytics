# Intent: Daily 06:00 UTC Airflow orchestration for Pokemon Analytics

## Classification

- **Action:** `work`
- **Kinds:** `orchestration` (one entry). The dlt pipeline and dbt project are already committed; this intent adds only the scheduled orchestrator that runs them together.

## Goal

Give the Pokemon Analytics domain a hands-off daily refresh: the PokeAPI dlt load lands `bronze.pokemon`, then the two dbt models (`stg_pokemon`, `pokemon_weight_bands`) build against it. Consumers: whoever queries the `marts.pokemon_weight_bands` table in the Fabric warehouse; today that is the internal test consumer of the VD-5578 domain, but the schedule holds for any downstream reader.

## Source system

- `ingestion/pokemon_pipeline.py` — committed dlt pipeline reading the public PokeAPI (no credential). Loads `bronze.pokemon` via the Fabric warehouse destination with OneLake staging.
- `transformation/` — committed dbt project (`profile: dbt_fabric`) with `stg_pokemon` (view) and `pokemon_weight_bands` (table).
- Availability constraint: PokeAPI is a public unauthenticated endpoint with no formal SLA. A transient upstream outage results in a failed DAG run for that day; recovery is a manual re-trigger. That behaviour is accepted, not compensated.

## Target

- **Platform:** `fabric_warehouse` (from `VD_DOMAIN_DATA_PLATFORM`).
- **Orchestration target:** `airflow` — per user instruction ("We use Airflow").
- **Domain secret backend:** `azure_key_vault` (from `VD_DOMAIN_SECRET_STORE_KIND`) — the precondition ADR-0026 names for the Airflow target is satisfied.
- **Deployed schedule:** daily at 06:00 UTC.
- **Item location:** `orchestration/PokemonDaily.ApacheAirflowJob/` plus the standard `orchestration/PokemonDaily.DataBuildToolJob/` (the managed dbt job the DAG triggers). Names are the design record's to finalise.

## Out of scope

- Any change to `ingestion/pokemon_pipeline.py` or the `transformation/` dbt project — both are already committed and correct for the workload.
- Any production deployment, schedule activation, or CI/CD wiring; the ship product is a repository PR carrying the committed native items. Activating the schedule in production is the customer's CI/CD path, per the orchestration playbook.
- Alerting / notification channels on failure (no consumer named); a failed DAG surfaces in Fabric's own run history.
- Backfill of historical days: `catchup=False` is the intended behaviour, and PokeAPI is a live source with no historical window.
- Data-quality tests beyond the acceptance rows above (dbt tests, if any, run as part of `dbt build`).
