# Plan: Daily 06:00 UTC Airflow orchestration for Pokemon Analytics

**Goal:** Author the Fabric Apache Airflow Job that runs the committed PokeAPI dlt load then the committed dbt project as one unit, and prove it runs end-to-end in the intent's ephemeral workspace before shipping.

**Approach:** Materialize the three committed native items — `pokemon_daily.ApacheAirflowJob`, `pokemon_daily.DataBuildToolJob`, and the reused `pokemon_dlt_runner.Notebook` — via the plugin's scripted templates, validate them statically, then apply them into the ephemeral workspace and trigger the DAG on demand. The design record `docs/design/pipelines/pokemon_daily.md` (backed by `docs/adr/0001-orchestration-target-is-apache-airflow.md`) carries every durable decision; this plan carries only what this intent is doing.

**Tech Stack:** Fabric REST API + Apache Airflow Job (Airflow 2.10.5, `apache-airflow-providers-microsoft-fabric==0.1.1`), Fabric Warehouse via `dbt-fabric` in a managed `.DataBuildToolJob`, dlt via a `.Notebook` runner, plugin scripts under `plugins/vibedata-data-engineering/_shared/references/dialects/fabric/` and `scripts/fabric/`.

## Global Constraints

- Active data platform is `fabric_warehouse` (`VD_DOMAIN_DATA_PLATFORM`); orchestration target is Apache Airflow (ADR-0001). No path substitutes another platform's tooling.
- Domain secret backend is `azure_key_vault` (`VD_DOMAIN_SECRET_STORE_KIND`) — precondition for the Airflow target and for the dlt runner's credential resolution.
- Committed DAG must carry `schedule=None`, `catchup=False`, `max_active_runs=1` (validator's `committed-active-schedule` rule; ADR-0001).
- Committed items must contain no literal workspace GUID, item id, connection string, or credential (validator's `committed-guid` rule).
- `orchestration_support.py` lives in `plugins/`, not `dags/` (Fabric silently drops non-DAG `.py` at the top of `dags/`; validator's `dropped-dag-module` rule).
- `airflowRequirements` = `apache-airflow-providers-microsoft-fabric==0.1.1` only. No dbt-flavoured packages (validator's `worker-side-dbt` rule).
- DAG leaf task is `workload_succeeded` (`EmptyOperator`, default `all_success`); `record_run` is `all_done` and cannot be the leaf (validator's `recorder-only-leaf` rule).
- The dbt job triggers via `MSFabricRunJobOperator(job_type="DataBuildToolJob")` with **no** `job_params`; the operation and selector live in `dbt-content.json`.
- Ephemeral destination for the sandbox run is `VD_EPHM_FABRIC_WAREHOUSE_*`; production coordinates are never targeted from this intent.
- On-demand DAG trigger is the sandbox proof; cadence stays inert until customer CI/CD activates it.
